# Legacy 兼容边界设计

> 日期：2026-06-08
>
> 状态：已实现
>
> 范围：租户工作台路由、主导航、历史链接和兼容期读取面。

## 1. 需求摘要

当前分支作为全新产品设计，需要明确是否继续兼容历史 dashboard/job 形态。结论是：兼容历史资产，不兼容历史产品形态。

功能性要求：

- 租户用户主流程必须从 `/projects/:tenantKey` 进入。
- 新页面、新导航和新 API 必须围绕项目模型组织，不再以 `job_id` 作为产品入口。
- 旧 dashboard/task 链接仍可直接访问，用于历史链接、交付排障和兼容期读取。
- 历史数据仍可通过兼容读取面或桥接字段追溯，不因为新设计而丢失。

非功能性要求：

- Legacy 入口不能绕过登录、租户授权和 Repository 租户过滤。
- 兼容层必须有测试约束，避免旧 job/task 页面重新进入主导航。
- 兼容策略应保持低运维复杂度，不为了删除旧入口引入一次性大迁移风险。

## 2. 决策

采用“兼容历史资产，不兼容历史产品形态”：

| 范围 | 保留策略 | 不保留策略 |
|------|----------|------------|
| 历史链接 | `/dashboard/:tenantKey/:jobId`、`/tasks/:tenantKey/status` 等仍可直接访问。 | 不重新放回默认入口、主侧边栏或新用户流程。 |
| 历史数据 | 旧 `job_id`、旧原始回答、旧分析事实和兼容期桥接字段继续可读取。 | 不让新项目功能继续围绕旧表或旧 URL 设计。 |
| 读取面 | dashboard 兼容页可继续读分析事实聚合结果。 | 不把 legacy dashboard 作为新指标、报告、告警或质量页的主模型。 |
| UI 形态 | 旧页面可作为排障入口保持可用。 | 不复刻旧视觉层级、旧导航结构或旧任务工作流。 |

## 3. 路由约束

前端以 `web/src/config/routes.js` 作为单一策略源：

- `getProductShapeRoutes()` 返回当前产品形态路由：项目列表、项目详情、项目数据质量和账户管理。
- `getLegacyCompatibilityRoutes()` 返回历史兼容路由：旧 dashboard、趋势、平台、信源、情感、问答快照和旧任务页。
- 当前产品形态路由不得要求 `jobId`。
- Legacy 路由可以参与 App route 生成，但不得参与主侧边栏菜单。

对应回归测试位于 `web/src/config/__tests__/routes.test.js`。

## 4. ADR

**决策**：新设计不兼容旧产品形态，只兼容历史资产。

**理由**：`tenant_key + job_id` 适合一次性采集批次，不适合长期品牌监测业务。继续让新功能围绕旧 job 入口扩展，会让项目、采集、分析、指标、报告和数据质量重新分裂成两套产品语义。保留历史链接和数据读取可以降低迁移风险，同时不阻碍新主线收敛。

**后果**：

- 后续新增租户工作台功能时，应优先进入 `/projects/:tenantKey` 或 `/projects/:tenantKey/:projectId` 族路由。
- 如果必须新增 legacy 能力，需要说明它服务的是历史链接、数据追溯或排障，而不是新用户流程。
- 删除 legacy 前需要另起清理阶段，确认历史链接替代方案、线上数据迁移、执行器协议和回归测试。

## 5. 删除条件

Legacy 兼容层可以在满足以下条件后单独评估删除：

- 历史 dashboard 链接有项目运行页或报告页替代。
- 旧 `job_id` 到新 `collection_job_id` / `project_id` 的映射已完成线上数据审计。
- 执行器 fetch/report 协议已完全迁移到 collection task 和 attempt。
- dashboard、问答快照、情感分析等读取面不再依赖旧明细兜底。
- 有独立 ExecPlan 覆盖路由删除、API 删除、数据库清理和客户迁移通知。
