# 租户访问授权与导入租户补授权规格

> 状态：已实现，2026-05-20 创建
>
> 本文档定义平台运营人员在已有租户、导入租户或历史数据租户上，为已有用户显式授予租户工作台访问权限的产品边界。架构原则见 `docs/ARCHITECTURE_MULTITENANT.md`，运行命令见 `docs/references/20260520-030000-tenant-access-grant-reference.md`。

## 1. 背景

平台管理员通过 `PLATFORM_ADMIN_EMAILS` 白名单登录后，拥有平台域权限，可以进入 `/platform/*` 管理租户元数据。后续 dashboard 读接口会提供平台管理员全租户只读旁路；但非平台用户、租户内写接口、或需要真实租户成员关系的场景，仍必须通过 `user_tenants` 授权。

当系统接入历史 SQLite/MySQL 数据、人工导入租户，或先 bootstrap 平台管理员再访问已有租户时，可能出现以下状态：

- `tenants` 表已有目标租户。
- `qa_brand_state`、`llm_conversations` 等业务表已有目标 `tenant_key` 和 `job_id` 的数据。
- 当前登录用户存在但不是平台管理员，或目标接口不属于 dashboard 只读范围。
- `user_tenants` 没有该用户与目标租户的成员关系。

此时访问租户工作台或租户内写接口应返回 403，而不是自动展示或修改数据。这是多租户隔离的预期行为，但需要提供明确的运营补授权能力。

## 2. 目标

1. 平台运营人员可以通过本地/部署 CLI，为已有非平台用户或需要真实 membership 的已有用户授予某个租户的 `viewer`、`member` 或 `admin` 角色。
2. 授权结果写入或更新 `user_tenants`，让后续所有业务 API 继续走统一的租户成员校验。
3. CLI 对未知用户、未知租户、停用用户、停用租户和非法角色失败退出。
4. 授权操作幂等：已有相同 active 成员关系不重复写入；已有不同角色按指定角色更新；停用成员关系可显式恢复为 active。

## 3. 非目标

1. 不用于平台管理员 dashboard 全租户只读访问；该能力由专用只读依赖表达。
2. 不新增公开 HTTP API 来授予租户访问权限。
3. 不在本阶段实现完整审计表、审批流或临时权限过期机制。
4. 不自动创建用户；用户创建仍通过 bootstrap、租户创建或员工注册流程完成。

## 4. 用户流程

### 4.1 导入租户补授权

1. 运维人员确认目标租户 `tenant_key` 和目标用户邮箱。
2. 运行租户访问授权 CLI，默认授予 `viewer` 角色。
3. CLI 校验用户和租户均存在且 active。
4. CLI 写入或更新 `user_tenants`。
5. 用户重新登录或刷新页面后，可访问该租户工作台。

### 4.2 平台管理员排障只读访问

平台管理员需要进入客户租户工作台排查数据展示问题时，应获得 `viewer` 角色。只有需要代客户加载任务或管理租户内资源时，才授予 `admin`。

## 5. 权限规则

| 场景 | 处理 |
|---|---|
| 用户不存在 | 失败，不自动创建 |
| 用户非 active | 失败，避免绕过账号处置 |
| 租户不存在 | 失败 |
| 租户非 active | 失败，避免访问停用租户 |
| 角色不是 `viewer/member/admin` | 失败 |
| 成员关系不存在 | 插入 active 成员关系 |
| 成员关系已 active 且角色相同 | 返回 already exists，不写入 |
| 成员关系已 active 但角色不同 | 更新为指定角色 |
| 成员关系 inactive/suspended | 更新角色并恢复为 active |

## 6. 验收标准

- 未建立 `user_tenants` 的用户访问租户工作台仍返回 403。
- CLI 授权后，`get_current_tenant` 能解析目标租户上下文。
- CLI 默认最小权限为 `viewer`。
- CLI 不输出密码、token、数据库连接串或 API Key。
- 后端目标测试、ruff 和文档校验通过。
