# Brand Analysis PRD

## Problem Statement

品牌、内容和增长团队正在面对一个新的监测问题：用户在不同 AI 平台上提问时，模型回答会塑造品牌认知，但这些回答通常分散在大量问答记录、引用链接和不同平台批次中。团队需要知道目标品牌是否被提及、是否处于首位或前三提及、情绪倾向如何、引用了哪些链接、引用链接是否来自已发布内容、内容类型是什么，以及这些结果能否沉淀到数据库供后续 BI 或业务系统使用。

当前痛点包括：

- AI 问答数据规模增长后，人工逐条判断品牌提及、引用状态和内容来源成本过高。
- 不同 LLM 平台、租户、任务批次、品牌、品类、关键词和日期窗口需要统一过滤与复盘。
- 品牌、竞品、引用链接和内容类型的判断需要结合规则、LLM 和人工维护的参考集合。
- 分析结果既要可追溯到原始对话，也要能按插件、日期和业务键稳定输出。
- LLM、MySQL、文件系统和配置都是外部边界，失败时必须可诊断，不能让批处理悄悄产生不可信结果。
- 团队需要一种可扩展插件机制，新增指标时不重写主流程，也不破坏已有输出和入库合同。

## Solution

Brand Analysis 提供一个配置驱动的 Python CLI/库式分析工具。用户通过配置文件声明数据库连接、启用插件、插件数据源、输出路径、LLM provider 和分析参数，然后通过命令行指定品牌、租户、任务批次、平台、日期窗口和竞品列表，系统自动读取 MySQL 数据源、按日期批次组织记录、调用插件分析、聚合结果、保存 JSON 输出，并在核心插件中将结果幂等写回业务表。

产品体验从用户角度表现为：

- 用户用一个命令启动指定品牌的批量分析。
- 用户不改代码即可启用或关闭 `mention_status`、`reference_status`、`extract_source`、`llm_ping`、`import_mention_data` 等插件。
- 用户可以针对多租户、多任务、多平台、多日期窗口和竞品列表做聚焦分析。
- 用户可以在输出目录中按插件和生成日期查看 JSON 结果。
- 用户可以在数据库中查询品牌状态和引用状态，供统计看板、报表或下游业务使用。
- 用户可以通过工具插件验证 LLM 服务连通性，或将历史 JSON 结果补导入数据库。
- 开发者可以通过统一插件合同扩展新的分析维度，并通过统一 LLM 适配层支持更多模型供应商。

## User Stories

1. 作为品牌分析师，我希望通过命令行对目标品牌进行品牌分析，以便快速评估该品牌在 AI 回答中的呈现情况。
2. 作为品牌分析师，我希望按租户筛选分析结果，以便只处理属于特定客户或业务单元的数据。
3. 作为品牌分析师，我希望按任务批次筛选分析结果，以便独立查看某次营销活动或监测运行。
4. 作为品牌分析师，我希望按平台筛选分析结果，以便对比不同 AI 平台对同一品牌的呈现差异。
5. 作为品牌分析师，我希望按生成日期范围筛选分析结果，以便回顾特定活动周期或事件窗口。
6. 作为品牌分析师，我希望分析结果按生成日期分组，以便日常趋势回顾和回溯变得简单直观。
7. 作为品牌分析师，我希望系统能识别目标品牌是否被提及，以便衡量基础的品牌曝光度。
8. 作为品牌分析师，我希望系统能识别目标品牌是否被首个提及，以便衡量第一提及率（top-of-mind awareness）。
9. 作为品牌分析师，我希望系统能识别目标品牌是否出现在前三提及中，以便评估接近头部的曝光水平。
10. 作为品牌分析师，我希望获得品牌提及的情感状态，以便区分正面、中性和负面的认知。
11. 作为品牌分析师，我希望能够传入竞品品牌，以便将目标品牌的曝光度与重要替代品牌进行对比。
12. 作为品牌分析师，我希望 AI 回答中发现的所有品牌都能被保留下来，以便追溯某个提及或排名是如何被分配的。
13. 作为内容策略师，我希望知道 AI 回答中引用了哪些 URL，以便理解来源影响力。
14. 作为内容策略师，我希望将引用的 URL 与已发布的 URL 列表进行匹配，以便判断 AI 回答是否引用了我们投放或自有的内容。
15. 作为内容策略师，我希望每条引用按内容类型分类，以便对比新闻、官网、社交媒体、电商、博客等不同来源类别。
16. 作为内容策略师，我希望内容类型分类具备基于规则的兜底机制，以便在 LLM 配置不可用时链接分类仍能正常工作。
17. 作为内容策略师，我希望在对比前对 URL 进行归一化处理，以免尾部斜杠、默认端口和片段造成误判不匹配。
18. 作为分析师，我希望支持 URL 来源提取，以便将原始链接转换为来源名称或域名。
19. 作为分析师，我希望 URL 来源提取在失败时能降级为域名提取，以便网络或 LLM 故障不会抹掉所有来源信号。
20. 作为运维用户，我希望有一个 LLM 连通性检测工具，以便在运行昂贵的分析之前验证供应商凭证、端点可用性和响应延迟。
21. 作为运维用户，我希望 LLM 连通性检测的错误信息包含状态码、超时和诊断详情，以便更快定位供应商问题。
22. 作为运维用户，我希望历史提及的 JSON 结果能导入数据库，以便无需重新运行所有 LLM 分析即可回填历史运行数据。
23. 作为 BI 消费者，我希望品牌提及状态持久化到一张稳定的表中，以便仪表盘能按对话查询品牌状态。
24. 作为 BI 消费者，我希望引用状态持久化到一张稳定的表中，以便仪表盘能查询已发布链接的状态、域名和内容类型。
25. 作为 BI 消费者，我希望数据库写入是幂等的，以便重新运行同一批次时更新已有行而不是重复产生指标数据。
26. 作为数据工程师，我希望插件数据源以声明式方式配置，以便新增表或视图时无需硬编码表访问逻辑即可进行分析。
27. 作为数据工程师，我希望在构建查询之前验证表名，以免配置的数据源产生不安全的 SQL 标识符。
28. 作为数据工程师，我希望配置的字段与实际表列取交集，以免表结构变更不必要地导致整次运行崩溃。
29. 作为数据工程师，我希望缺失的可选列能优雅降级，以便表结构不完整时仍能尽可能产出有用的结果。
30. 作为数据工程师，我希望在可用时使用 `generated_date` 进行输出分批，以便结果与源数据的时间线对齐。
31. 作为数据工程师，我希望没有生成日期的记录被归入一个明确的"未知日期"桶中，以免它们被静默丢弃。
32. 作为开发者，我希望有一个稳定的插件接口，以便新增指标时无需重写分析器的编排逻辑。
33. 作为开发者，我希望插件注册时包含元数据，以便插件类型、LLM 需求和默认启用状态可被自动发现。
34. 作为开发者，我希望插件能接收全局应用配置和插件专属配置，以便插件特定行为与主分析器保持隔离。
35. 作为开发者，我希望有一个共享的 LLM 操作器，以便不同供应商的差异被隔离在统一接口之后。
36. 作为开发者，我希望支持 OpenAI 兼容适配器和供应商专属适配器，以便能对接 OpenAI、智谱AI、硅基流动、DeepSeek 以及自定义端点。
37. 作为开发者，我希望 LLM 调用包含超时、重试和错误对象，以便插件代码能区分可重试和不可重试的失败。
38. 作为开发者，我希望默认测试无需真实的 LLM 凭证即可运行，以便贡献者能在本地和 CI 环境中验证行为。
39. 作为维护者，我希望真实供应商测试由环境变量控制开关，以便线上冒烟测试是有意为之且不会泄露密钥。
40. 作为维护者，我希望密钥不出现在文档、日志和示例中，以免 API 密钥、数据库密码和客户数据被暴露。
41. 作为维护者，我希望文档按架构、设计、安全、参考、产品规格和执行计划进行组织，以便未来的 AI 代理能安全地恢复上下文。
42. 作为维护者，我希望有文档校验机制，以便尽早发现断链入口或缺失的协作文档。
43. 作为维护者，我希望技术债务与产品规格分开追踪，以免已知的打包、配置和测试隔离问题被遗漏。
44. 作为 CLI 用户，我希望在品牌缺失、日期无效或配置无效时看到清晰的校验错误，以便无需阅读代码就能修正输入。
45. 作为 CLI 用户，我希望输出文件名包含时间戳和唯一标识，以便重复运行时不会覆盖之前的产物。
46. 作为 CLI 用户，我希望在配置开启时输出格式化的 JSON，以便输出产物更易于人工查看。
47. 作为平台运维，我希望日志中包含插件、表和供应商的上下文信息，以便多插件批量运行时能诊断故障。
48. 作为平台运维，我希望单个插件失败时尽可能以结构化插件错误的形式返回，以便批量运行能明确报告部分问题。
49. 作为产品负责人，我希望该工具目前保持 CLI/库的形态，以便团队在添加 UI 之前专注于可靠的分析能力。
50. 作为产品负责人，我希望新的可见行为在实现之前先在产品规格中描述清楚，以便范围和验收标准明确无误。

## Implementation Decisions

- 将分析器编排视为产品工作流协调器。它负责配置加载、CLI 参数解析、已启用插件的解析、数据源分组、数据库读取、日期分批、插件调用、结果聚合、输出持久化和高层错误报告。
- 将插件合同作为主要扩展机制。新的分析维度应实现共享插件接口并通过元数据注册自身，而不是在主分析器中添加特化分支。
- 区分指标插件和工具插件两个类别。指标插件分析数据源行并产出聚合结果；工具插件执行运维任务，如 LLM 连通性检查或 JSON 导入。
- 保持数据源配置声明式。插件可以指定带表和字段的 `datasources`，或为兼容性指定单个表，但表名和字段必须在边界处校验。
- 在所有分析输出中保留多租户和批次标识。租户键、任务 ID、对话 ID、平台、品牌、品类、关键词和生成日期是核心业务标识符。
- 将生成日期分批作为产品行为保留。它提供可预测的输出分组，并使 JSON 产物与源数据时间线对齐。
- 继续将插件结果写入按插件、按日期划分的 JSON 产物。这些文件对审计、调试和回填工作流很有用。
- 继续对品牌状态和引用状态使用幂等的数据库写入。重跑应更新业务记录，而不是创建重复的分析行。
- 将 LLM 供应商集成置于统一的操作器和适配器层之后。插件应通过共享服务请求品牌识别、内容类型分类或来源提取，而不是直接绑定到某个供应商。
- 保持依赖 LLM 的插件具备显式失败或降级能力。引用内容类型和来源提取可降级为规则/域名；提及状态需要有效的 LLM 配置才能进行高质量的品牌识别和情感评分。
- 将已发布 URL 匹配视为确定性深模块。它应将 URL 加载、归一化和比较封装在一个简单接口之后，便于独立测试。
- 将内容类型分类视为深模块。它应在稳定接口之后组合确定性规则和可选的 LLM 分类，具有固定的类别词汇和 JSON 输出预期。
- 将品牌提及识别视为深模块。它应将品牌提取、排序、变体匹配、竞品对比和情感评分封装在稳定的结果合同之后。
- 将数据源行归一化视为深模块机会。查询/回答文本构建、降级文本提取、对话 ID 选择和业务元数据提取应可独立测试。
- 将导入/回填视为深模块机会。JSON 载荷解析、日期推断、行构建、去重和数据库插入应与插件编排保持分离。
- 保持安全约束持久有效。密钥必须通过私有配置或环境变量提供，且不得出现在日志、公开文档或示例中。
- 保持当前 CLI 作为主要界面。本 PRD 不要求 Web UI、调度器、仪表盘或托管服务。
- 将文档视为产品界面的一部分。架构、设计、安全、参考和产品规格是 AI 代理安全协作和维护所必需的。
- 已知的打包不一致性仍是一个实现风险。在将包分发路径视为受支持的产品界面之前，应先协调安装命令入口点与实际导入包布局。
- 当前本地配置包含数据库连接字段，在广泛分享之前应拆分为安全的示例配置和私有的本地/部署配置。

## Testing Decisions

- 好的测试应验证外部行为和稳定合同，而非实现细节。对本项目而言，这意味着测试插件输出、聚合结果、CLI 校验、配置校验、数据源归一化、URL 归一化、数据库行构建和 LLM 错误处理。
- 默认测试应为离线且确定性的。应使用模拟 LLM 响应、伪造数据源行和临时输出路径，而非真实供应商凭证或生产数据库访问。
- 线上 LLM 测试应通过显式环境变量选择性开启。凭证缺失或无效时应干净跳过。
- 数据库集成测试应使用受控的本地测试数据库，或将 SQL 行构建逻辑与实际写入隔离。测试不得依赖生产凭证。
- 分析器编排应围绕可见行为进行测试：从配置选择插件、工具插件执行、表数据源分组、日期分批、行文本构建、插件聚合和输出保存结构。
- 插件注册表和插件管理器应测试发现、启用/禁用行为、LLM 需求处理和配置注入。
- 提及状态测试应覆盖目标品牌提及、首位提及、前三提及、竞品状态、情感状态映射、聚合摘要和 qa 品牌状态行生成。
- 引用状态测试应覆盖 URL 归一化、已发布 URL 匹配、内容类型规则降级、LLM 分类降级行为、聚合摘要和 qa 引用行生成。
- 来源提取测试应覆盖 URL 提取、去重、域名降级和来源计数聚合。
- 导入提及数据测试应覆盖 JSON 载荷解析、日期推断、重复处理、跳过行统计和导入统计。
- LLM 操作器测试应覆盖操作器创建、供应商配置映射、同步/异步行为、流式行为、缓存/统计行为、结构化错误处理和可重试错误分类。
- 安全导向测试应覆盖无效表名、缺失必填配置字段、无效日期过滤器，以及在可行范围内防止返回的配置摘要或日志中泄露密钥。
- 文档校验应作为 PRD 驱动工作的验收套件的一部分：`python scripts/validate_agents_docs.py --level WARN`。
- 测试套件中已有的先例包括：统一 LLM 操作器、LLM 操作器行为、引用状态聚合、保存插件批次结果、导入提及数据、品牌识别和模拟使用示例的单元测试。

## Out of Scope

- 构建 Web 仪表盘、Web API、GUI 或托管 SaaS 界面。
- 构建调度器、队列工作器或执行器编排服务。
- 定义超出使用数据源记录中现有租户键的身份认证、用户管理或租户入驻流程。
- 将 MySQL 替换为其他数据库。
- 保证对不暴露可用文本或插件所需字段的任意非结构化表的分析。
- 保证线上 LLM 可用性或供应商定价行为。
- 对每条 LLM 分类结果进行人工审核。
- 作为本 PRD 的一部分将所有现有插件重写为新架构。
- 实现完整的数据库表结构变更迁移框架。
- 发布敏感的本地配置、`.env` 值或生产数据示例。
- 支持实时流式分析；当前行为是面向批处理的。

## Further Notes

- 本 PRD 描述了当前产品基线和从仓库推断出的近期产品合同。它应被视为未来功能规格的产品级唯一真相来源，针对个别行为变更创建更细粒度的规格。
- 最高优先级的就绪问题是：将安全的示例配置与私有本地配置分离，因为该工具处理数据库凭证和 LLM 密钥。
- 最有价值的深模块提取机会是：数据源行归一化、已发布 URL 匹配、内容类型分类、品牌提及识别和导入/回填行构建。
- 项目应在承诺将安装后的 CLI 用法作为受支持的客户工作流之前，先理顺其包分发方案。在此之前，`python -m src` 仍是已验证的 CLI 入口。
- to-prd skill 要求将 PRD 发布到带 `needs-triage` 标签的议题跟踪器，但本次仓库会话未提供议题跟踪器集成或分类标签词汇。因此本 PRD 先作为项目产品规格文档创建。
